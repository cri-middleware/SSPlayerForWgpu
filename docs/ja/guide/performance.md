# パフォーマンス

まず**「数字が言うまで性能問題は無い」**という前提から始めてください。このページはその数字の取り方と、
実際にコストになる数少ないものについてです。

## たいてい速い理由

構造上の事実が 3 つあり、どれもあなたが何かをする必要はありません：

* **頂点バッファがありません。** CPU はパーツ 1 つにつき 80 バイトのプリミティブを 1 つ書き、頂点ステージが
  `@builtin(vertex_index)` から展開します。頂点ごとの書き込みはゼロなので、200 パーツのキャラクターは
  800 頂点ではなく 200 個の小さな書き込みです。
* **アトラスのアップロードはデバイスごとに 1 回。** テクスチャマップはデバイススコープなので、同じパックを
  5 体表示してもアップロードは 1 回です。
* **キャスト全体で 1 レンダーパス。** 同じターゲットの全キャラクターが 1 回の `update` と 1 つのパスを
  通ります。2 体目のコストは再生ツリーだけです。

残るコストはスループットではなく表現力の側にあります。

## カウンタを読む

=== "Rust"

    ```rust
    let s = scene.stats();
    println!("{} players, {} prims, {} draws, {} bytes", s.players, s.prims, s.draw_calls, s.uploaded_bytes);
    ```

=== "C"

    ```c
    ss_scene_stats_t s;
    ss_scene_stats(scene, &s);
    ```

=== "JavaScript"

    ```js
    const s = surface.stats();   // { players, prims, drawCalls, uploadedBytes, ... }
    ```

| カウンタ | 意味 | Rust | C | JS |
|---|---|:--:|:--:|:--:|
| `players` | このフレームにジオメトリを出したキャラクター数 | ✅ | ✅ | ✅ |
| `prims` | フレーム内のパーツ・シェイプ・エフェクト粒子 | ✅ | ✅ | ✅ |
| `draw_calls` | 記録されたドロー数。`prims` との差がマージ余地 | ✅ | ✅ | ✅ |
| `uploaded_bytes` | フレームのストレージバッファへの書き込み量 | ✅ | ✅ | ✅ |
| `mergeable_draws` | ドローリストのうちマージ*できる*量 | ✅ | — | ✅ |
| `redundant_texture_binds` | 既にバインド済みのテクスチャを貼り直したドロー数 | ✅ | — | ✅ |
| `coverage_layers` | このフレームのマスクカバレッジパス数 — カバレッジバックエンドのコスト | ✅ | — | — |
| `gpu_pass_time_ns` | 直近の計測パスの GPU 時間 | ✅ | ✅ | ✅ |

ネイティブビューアはどちらもこれを毎秒表示するので、自分のデータで確認する最短経路は
`cargo run -p ssplayer-wgpu-viewer` に `.ssab` をドロップすることです。

## GPU 時間

`gpu_pass_time_ns` にはタイムスタンプクエリ付きで作られたデバイスが必要です（Web ではブラウザが
`timestamp-query` を許可していること）。無い場合は `None` / `0` / `undefined` になり、他のカウンタは
そのまま使えます。

値は**設計上 1〜2 フレーム遅れて**返ります。最新にするにはパイプラインをストールさせる必要があり、
それは測ろうとしているものを変えてしまいます。**最新にするためのストールを足さないでください。**

## 変更を計測する

痛い目を見て学んだ規則が 2 つ：

1. **前後で計測する。** 「速くなるに決まっている」構造変更が、実際にはそうでないことはよくあります。
2. **本物のフレームループで回す。** `update` とレンダーパスをフレームと同じように交互に実行してください。
   別々のループで測ると、フレームを跨いでキャッシュするものが実際よりずっと良く見えます。

`cargo test --test scale -- --ignored` はこのリポジトリのスループット計測で、両方を満たしています。
CI のソフトウェア GPU では速度を判定できないので `#[ignore]` されています。

!!! warning "緑のレンダリングテストを疑う"
    オフスクリーン描画テストは GPU アダプタが無い環境では自分をスキップするので、そういうマシンでの
    成功は何も検証していない可能性があります。ラスタライズを変更したときは、リードバックを PNG に落として
    目で見てください。ピクセル数だけでは実際の退行を見逃したことがあります。

## 実際にコストになるもの

| | |
|---|---|
| **カバレッジマスクバックエンド** | **マスクを使うキャラクター 1 体につき 1 パス／フレーム**。このライブラリで最大のキャラクター単位コストであり、ステンシルがある環境で[カバレッジが既定でない理由](./masks.md)です |
| **アトラスの種類が多い** | それぞれがバインドグループの切り替えです。`redundant_texture_binds` を見れば、描画順が足を引っ張っているか分かります |
| **キャラクターが非常に多い** | キャラクター単位の CPU 走査は設計上シングルスレッドです（下記） |
| **非表示にする vs 描かない** | `set_visible(false)` はタイムラインの前進ごとスキップするので、カリングしたキャラクターのコストはゼロです。画面外のキャストにはこれを使ってください |

## 計測したうえで意図的に採用しなかったもの

見落としではありません。256 体のフレームに対して検討済みです：

* ドローコールのマージ、バインドグループの重複排除、レンダーバンドル、シェイプの間接描画；
* バインドレステクスチャ — これは WebGPU で利用できないという事情もあります；
* キャラクター単位のフレーム走査のスレッド化。（ロード時の**アトラスデコードは**スレッド化されており、
  呼び出しが返る前に消えるスコープの中で行われます。）

理由は [ROADMAP](https://github.com/cri-middleware/SSPlayerForWgpu/blob/main/ROADMAP.md) の
*Deliberate non-goals* にあります。`mergeable_draws` と `redundant_texture_binds` は、その前提を自分の
データで確かめられるように公開されています。あなたのシーンでこれらが大きいなら、それは報告に値します。
