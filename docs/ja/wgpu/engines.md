# エンジンへの組み込み

すでに `wgpu::Device` を持っているエンジンに Player を組み込むのは **Rust 限定**の機能で、Player の
feature ではなく*アダプタクレート*として提供されます。

## アダプタを別クレートにする理由

`ssplayer-wgpu` はどのエンジンにも依存しませんし、依存してはいけません。理由は実務的な 2 つです：

* Player クレートにエンジン依存が入ると、そのエンジンを使うかどうかに関わらず、全採用者がそのエンジンのリリーススケジュールに縛られます；
* アダプタは自分のエンジンの系列（もし将来 wgpu メジャーが Player と分岐したならそれも含めて）に追随でき、Player を引きずりません。

そのため `ssplayer-bevy` は Player の隣で独立にバージョン管理され、今後のアダプタも同じ形になります。

## wgpu のバージョン固定 { #the-wgpu-pin }

**wgpu はリポジトリ全体で 30 系に固定されています。**

Cargo の workspace はちょうど 1 つの `wgpu` に解決し、wgpu のメジャーが 2 つあるということは互換性のない型が 2 組あって、その間を橋渡しするものは無いということです。つまりこの固定は好みではなく互換性の契約です：

| 制約 | |
|---|---|
| `bevy_render` 0.20 | `wgpu ^30` を要求 |
| Slint の `unstable-wgpu-NN` | wgpu メジャーの**厳密一致**を要求。そして Vtuber アプリは Slint UI とこの Player を 1 デバイス上で合成します |

上げる前に Slint の対応メジャーを確認してください。不一致が実行時の驚きではなくコンパイルエラーになるのは、この状況で唯一ありがたい点です。

## アダプタがやるべきこと

Bevy アダプタが実例です。それ以外も次の 5 点は同じです。

1. **`SSRenderer` をデバイススコープで持つ** — エンジンのデバイスごとに 1 つ。ビューごと・キャラクターごとではありません。
2. **`SSScene` を描画ターゲットごとに持つ**。そのターゲットのカラーフォーマットに対して構築し、フォーマットが変わったら（HDR カメラ、別のスワップチェーン）作り直します。
3. **`update` と `draw` をエンジン自身のパスの中で実行する**。そのターゲットに描く他のものとの順序は*明示的な*エッジで指定します。encoder を開く 2 つのシステムは、指定しなければ競合します。
4. **マスクバックエンドは「パスが貸せるもの」から選ぶ**。アニメーションから選ぶのではありません。ステンシルアタッチメントがあれば `Stencil`、無ければ `Coverage`（焼き込みは本描画パスと同じ encoder に）。[マスク](../guide/masks.md)を参照。
5. **エンジンのアセットシステムがあるなら `load_with` に差し込む**。ファイルシステムを直接読まないこと。[ロードとアセット](../guide/loading.md)を参照。

そのうえで、エンジンのライフサイクルを Player のそれに対応付けます。デバイスロスト（外側へ向かって作り直す）、ウィンドウリサイズ（投影し直す）、そしてエンジンが「このエンティティは消えた」と呼ぶもの。

## 実例：Bevy

Bevy は 2 つのワールドで描画するので、アダプタもその継ぎ目で分かれています。3 つのコンポーネントはメインワールドにあり、extract がそれとフレームのデルタをレンダーワールドへコピーし、再生ツリー・レンダラー・シーンはすべてレンダー側にあります。Player が Bevy のデバイスを所有することはありません。描画システムがそのフレームだけ貸し出します。winit ビューアや C++ ホストと同じ借用モデルです。

真似する価値のある判断が 3 つ：

* **カバレッジマスク**。Bevy の 2D 深度は `Depth32Float` でステンシルを持たないためです。Bevy のアタッチメントには何も要求せず、描画は Bevy 自身のパス内に収まります。
* **明示的な `after(main_transparent_pass_2d)`**。同じ set に入れるだけでは不十分です。
* **Bevy の `Transform` ではなく独自のトランスフォームコンポーネント**。3D アフィンを Player の 5 つのスカラーへ分解するのは非可逆だからです。連動させたいアプリはコピーするシステムを 1 つ書き、どちらを正とするかを自分で決められます。

[Bevy リファレンス](../reference/bevy.md)も参照してください。

## Slint / egui / macroquad / 自作レンダラー

適合作業はありません。これらはデバイスとレンダーパスを渡してくれるので、[借用モデル](./borrow-model.md)が求めるものがそのまま揃っています。デバイスの隣に `SSRenderer` を 1 つ、ターゲットごとに `SSScene` を 1 つ持ち、フレームの中で `update` / `draw` を呼ぶだけです。

wgpu のバージョン固定がそもそも存在する理由は Slint のケースです。Slint UI とこの Player を 1 デバイス上で合成するには、Slint の `unstable-wgpu-<major>` feature が Player の解決するメジャーと一致している必要があります。

## できないこと

**エンジンが C ABI 経由で Player にデバイスを共有することはできません。** wgpu の型は C 境界を越えられず、
`Device` や `Queue` を渡す安定した表現が存在しないためです。したがってエンジンへの組み込みは、省略ではなく構造上、Rust 限定の機能です。

C から合成したい場合の経路はオフスクリーン描画＋テクスチャ共有です。Player に自分のデバイスを持たせ、テクスチャへ描画し、そのテクスチャを既存の interop でエンジンへ持ち込みます。[制限事項](../limitations.md#no-device-sharing-across-the-c-abi)を参照。
