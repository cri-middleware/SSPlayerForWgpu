# 借用モデル

!!! info "このページの対象"
    `wgpu::Device` を自分で持っている Rust アプリケーション、またはエンジンアダプタを書く人。
    [C](../start/cpp.md) や [Web](../start/web.md) のパスから来た場合、ここは読まなくて構いません。
    それらの Face はデバイスを自分で持ってくれます。

**Player は wgpu の `Device` / `Queue` / `Surface` / `SSRenderer` を所有しません。所有するのはあなたで、
フレームごとに貸し出します。**

この 1 つの決定によって、1 本のライブラリがスタンドアロンウィンドウ・ブラウザのキャンバス・C++
アプリケーション・既にデバイスを持っているエンジンのすべてを、どれも特別扱いせずに賄えます。
そしてあなたにレンダラーを明け渡させることもありません。

## 見た目

```rust
// 実行中ずっとあなたのもの。
let (device, queue) = ...;

// フレームごとに貸し出す。
scene.update(&mut renderer, &device, &queue, dt, &mut players);
scene.draw(&renderer, &mut rpass);   // *あなたが*所有する encoder 上の、*あなたが*開いたパス
```

Player は呼び出しの間だけ借りて返します。フレームを跨いで保持するものはありません。

## リソースの寿命が 3 通りだからスコープが 3 つ

| スコープ | 型 | 保持するもの | 作り直すとき |
|---|---|---|---|
| デバイス | `SSRenderer` | パイプライン、バインドグループレイアウト、サンプラー、アトラステクスチャ | デバイスロスト時 |
| 描画ターゲット | `SSScene` | 投影 uniform、フレームのジオメトリアリーナ、ドローリスト | ターゲットの**フォーマット**が変わったとき |
| キャラクター | `SSPlayer` | 再生ツリー、トランスフォーム、描画順、表示、アルファ | 作り直し不要 — GPU リソースを持たないため |

これを維持する規則が 1 つ：**`SSPlayer` に wgpu の型のフィールドを持たせてはいけません。** キャラクターが
テクスチャやバッファやデバイスを持った瞬間、「1 キャンバス＝1 キャラクター」が戻ってきます。そうなると
キャンバスごとにデバイスが、キャラクターごとにパイプラインセットが、そしてアトラスが「デバイスごとに 1 回」
ではなく「キャラクターごとに 1 回」アップロードされます。

デバイスはアプリケーション（またはページ）に 1 つ。キャンバスごと・ウィンドウごとの `request_device` は
決してしないでください。

## データ所有も双方向

借用モデルは wgpu ハンドルだけの話ではありません：

| データ | 所有 | 借用 |
|---|---|---|
| `.ssab` | Player | ランタイム |
| フレームデータ / SoA バッファ | ランタイム | Player — **フレームを跨いで保持しません** |
| GPU テクスチャ | あなた、または利便性としてレンダラー | レンダラーのバインドグループ |

`SSRenderer::set_texture` は**あなたが**所有する `TextureView` を受け取ってバインドグループを作るだけで、
`upload_texture` は「たまたまテクスチャ自体も作る」利便性の経路です。この非対称は意図的です。GPU
テクスチャを所有すると、エンジンのアセットシステム（Bevy の `Assets<Image>` と
`RenderAssets<GpuImage>`、Unity、Unreal）と 2 つ目のライフサイクルが競合し、その勝負に負けるのは常に
Player の側だからです。

`SSPack` が持つのは CPU 側のデータだけです。

## レンダーパスに求められること

| | |
|---|---|
| **カラーフォーマット** | `SceneConfig::color_format` と一致していること。パイプラインはこれに対して焼かれるので、変わるなら `SSScene` を作り直します |
| **MSAA** | オフ。パイプラインはシングルサンプルです |
| **ステンシル** | `MaskBackend::Stencil` を選んだ場合に限り必須。宣言したフォーマットで、描画する**全パス**に付けます |
| **色空間** | Player はアトラスのバイト列をそのまま書き、**色管理を一切しません**。sRGB ターゲットでは二重にエンコードされて明るくなりすぎます。非 sRGB ターゲットを渡すか、sRGB 空間で合成してください |

## 既存のレンダーグラフへ組み込む

フレーム内の順序は決まっていて、微妙なのは 1 か所だけです：

```rust
// 1. CPU：このターゲットの全キャラクターを進め、ジオメトリを構築する。
scene.update(&mut renderer, &device, &queue, dt, &mut players);

// 2. このシーンがカバレッジでマスクするなら、ビットマップを焼く —
//    下の本描画パスと同じ encoder に。
scene.encode_mask_coverage(&mut renderer, &device, &mut encoder);

// 3. 自分のグラフの適切な位置で、自分のパスに描画を記録する。
let mut rpass = encoder.begin_render_pass(&descriptor);
scene.draw(&renderer, &mut rpass);
```

微妙なのは 2 です。1 つの `CommandEncoder` の中のパスは順に実行されるため、マスクビットマップとそれを
サンプルする変換がどちらも「このフレームのもの」になります。encoder・システム・フレームを跨いで分けると、
この Player には無いはずのマスク 1 フレーム遅延が戻ってきます。

同じターゲットに他のシステムも描くなら、その encoder との順序は**明示的なエッジ**でなければならず、
同じ set に入れるだけでは足りません。レンダーコンテキストを取る 2 つのシステムはそれぞれ自分の encoder を
持ち、どちらのバッファが先にキューへ届くかは指定しなければ競合します（Bevy アダプタの描画システムが
`main_transparent_pass_2d` の後に明示的に順序付けされているのはこのためです）。

## 複数ターゲット、1 デバイス

`SSScene` は描画ターゲットごとで、デバイススコープのレンダラーを共有します：

```rust
let mut renderer = SSRenderer::new(&device);        // 1 回だけ
let mut main   = SSScene::new(&device, &main_config);
let mut minimap = SSScene::new(&device, &minimap_config);
```

どちらも同じパックを 1 回のアトラスアップロードから描きます。回帰テスト
（`tests/pack.rs::scenes_share_one_renderer`）がこれを固定しています。

!!! note "1 キャラクターにつき 1 フレーム 1 回の `update`"
    `SSScene::update` はタイムラインの前進とジオメトリ構築を一体で行います。同じキャラクターを 1 フレーム内で
    2 つのシーンの `update` に渡すと、**2 回進みます**。したがって 1 つのキャストを 2 つのビューに描くことは
    まだできません（Bevy アダプタは 2 つ目以降のビューを警告付きでスキップします）。

## 頂点バッファが無い理由

ランタイムの structure-of-arrays データはシーンのアリーナへコピーされ、頂点ステージが
`@builtin(vertex_index)` から展開します。CPU が書くのはパーツ 1 つにつき 80 バイトのプリミティブだけで、
頂点ごとには何も書きません。

利用側にとっての意味：キャラクターのコストはパーツ数に比例し、それが展開される頂点数には比例しません。
そして、あなたが用意・共有・リサイズすべき頂点バッファは存在しません。

## デバイスロスト

外側へ向かって作り直します — レンダラー、シーン、キャラクターの順。キャラクターが自分のアトラスを
レンダラー*へ*登録するためです。[デバイスロスト](../guide/device-loss.md)を参照。
